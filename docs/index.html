Head to Head

关键能力对比

以需求文档为标尺逐项核对，差异集中在工程化自觉性、沙箱实现深度与交付完整度上。

01

沙箱实现

GLM 挂起创建 + Job Object + 受限令牌最贴近需求；DeepSeek 完整三层思路；MiMo 扩展点 + 回退层。

02

工程化

DeepSeek 全场唯一闭环：start/test/lint/migrate 脚本齐备；MiMo 次之；GLM 需手动启动。

03

功能覆盖

DeepSeek 21 个路由模块覆盖最广；MiMo 19 个紧随其后；GLM 13 个存在合并或简化。

04

测试保障

DeepSeek api + unit 双套测试；MiMo 4 个测试文件；GLM 仅 run-all.js，业务测试近乎空白。

05

权限与可见性

DeepSeek 独立 groups + visibility 服务，隐私开关、免密切换全数落地，最贴近需求 3.9。

06

AI 能力

三者均覆盖安全审查 / 提示 / 数据生成；GLM 独立 injection.js 模块，注入防护最显式。

07

稳定性预期

DeepSeek 风险最低；MiMo 中低（轮询采样有漏检窗口）；GLM 中高（集成风险最大）。

08

文档体验

DeepSeek README + AGENTS.md + docs 最系统；GLM 沙箱原理讲解最深入但缺工程化指引。

Selection Guide

大模型编程选型建议

基于本次同题实测提炼，按任务类型选择合适的模型，事半功倍。

从零搭建完整工程

选 DeepSeek-V4.1。自发补齐测试 / lint / 启动脚本 / 迁移脚本，具备产品思维而非仅代码思维，交付物第二天还能维护。

底层 / 系统级攻坚

选 GLM-5.3。遇到 Windows API、C# 互操作等硬核技术点时会下钻到最深实现，技术含金量最高，需配人工工程化收尾。

快速铺功能原型

选 MiMo-V2.6。功能覆盖广、交付速度快、状态标注诚实，便于二次开发接手，可接受后期补全。

通用原则

  • 看工程化自觉性，不只看代码行数
  • 警惕"功能清单很长但收尾仓促"，逐条验收需求
  • 技术深度与交付完整度往往不可兼得
  • 分模块多轮驱动，降低长上下文烂尾率

评测三件套

  • 功能完整性：对照需求逐项勾验
  • 缺陷密度：静态审查 + 测试通过率
  • 可用性：能否 10 分钟内跑起来
  • 该框架可复用到其他模型横评
FAQ

常见问题

评测是怎么进行的？

三款模型依据同一份 NoldOJ 需求文档（约 480 行、30+ 功能模块）独立完成实现。评测采用只读代码评审：统计路由模块数与测试文件数，重点阅读沙箱、判题队列、AI、权限可见性等核心实现，不实际运行判题以避免环境差异干扰。

评分依据是什么？

三个维度各 10 分：功能完整性（对照需求逐项勾验）、bug 数量及严重等级（工程化水平 + 静态审查推断的稳定性风险）、用户体验（文档 / 配置 / 部署 / 界面预期）。

三份实现有何共同点？

均为零构建方案：Node.js ≥ 24 + 内置 node:sqlite、纯 vanilla JS 前端、Windows 原生沙箱（Job Object / 受限令牌）、SVG 验证码、双 Token 认证、WebSocket 实时推送、AI 安全审查（Ollama）等。

在哪里看完整评测报告？

仓库根目录的 README.md 与 evaluation_report.md；三份完整源码分别在 DeepSeek-V4.1-Flash/、GLM-5.3-Flash/、MiMo-V2.6-Flash/ 目录下。

结论可以直接照搬吗？

选型建议基于本次单命题实测，模型表现与任务类型、提示词、上下文长度强相关。建议将"评测三件套"（功能完整性 / 缺陷密度 / 可用性）作为固定框架，在自己的真实任务上复测后再定型。
