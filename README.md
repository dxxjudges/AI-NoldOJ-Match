# AI-NoldOJ-Match：三款大模型同题开发 NoldOJ 横向评测

> 同一道命题（[NoldOJ 需求文档](https://github.com/dxxjudges/AI-NoldOJ-Match/blob/main/NoldOJ_Requirements_Document.md)），分别由 **DeepSeek-V4.1-Flash**、**GLM-5.3-Flash**、**MiMo-V2.6-Flash** 三款大模型独立完成完整工程实现。
> 本仓库记录横向评测结果：**功能完整性 / bug 数量及严重等级 / 用户体验** 三个维度。

## 评测方法

- 以需求文档约 480 行、30+ 个功能模块（Windows 原生沙箱、多语言判题、AI 安全审查、考试系统、查重、虚拟比赛等）为唯一命题；
- 只读代码评审：统计路由模块数、测试文件数、脚本完备性，重点阅读沙箱、判题队列、AI、权限可见性等核心实现；
- 不实际运行判题（避免环境差异干扰），以代码完整度与工程化水平推断质量。

## 大模型编程选型建议

> 基于本次同题实测，给出不同场景下的选型参考。

### 1. 按任务类型选择

| 场景 | 推荐 | 理由 |
|------|------|------|
| **从零搭建完整工程（长周期项目、脚手架）** | DeepSeek-V4.1 | 自发补充测试/lint/启动脚本/迁移脚本，具备"产品思维"而非仅"代码思维"，交付物可直接使用 |
| **底层/系统级难点攻坚（沙箱、驱动、协议）** | GLM-5.3 | 遇到硬核技术点（Windows API、C# 互操作）时会下钻到最深的实现，代码技术含金量高 |
| **快速出全功能原型、功能铺量** | MiMo-V2.6 | 功能覆盖广、交付速度快、诚实的状态标注便于二次开发接手 |

### 2. 通用选型原则（从本次评测提炼）

1. **看工程化自觉性，不只看代码行数**：DeepSeek 赢在没有被明确要求的情况下主动补齐 AGENTS.md、CI、迁移脚本——这类模型生成的项目"第二天还能维护"。
2. **警惕"功能清单很长但收尾仓促"**：MiMo 覆盖面最广，但自行标注了"部分完成/留待扩展"；GLM 路由数明显偏少，可能存在静默简化。**交付前务必核对需求逐条验收**。
3. **技术深度与交付完整度往往不可兼得**：GLM 在沙箱上做到了三者最佳，但 package.json 连 start 脚本都没有。若团队有工程化底座（模板仓库/CI），GLM 的产出价值会放大；若没有，选 DeepSeek 这类"全栈自觉型"更稳。
4. **复杂度预算要前置**：三个模型都倾向把需求文档全部实现，导致单轮上下文极长。实际使用中建议**分模块多轮驱动**（先核心判题→沙箱→外围功能），能有效降低烂尾率。
5. **评分维度建议固定为三件套**：功能完整性（对照需求逐项勾验）、缺陷密度（静态审查 + 测试通过率）、可用性（能否 10 分钟内跑起来）。本次评测即按此执行，可复用到其他模型横评。

### 3. 一句话结论

- 要**能直接上线的完整工程** → 选 **DeepSeek-V4.1**
- 要**啃底层硬骨头** → 选 **GLM-5.3**（配人工工程化收尾）
- 要**快速铺功能、可接受后期补全** → 选 **MiMo-V2.6**
